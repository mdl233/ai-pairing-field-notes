# 第一部分 · 电脑上的东西到底是什么

## 1.1 文件与文件夹：电脑里的一切都是文件

**一句话**：程序、文档、图片、配置、日志、甚至"设置"本身，在系统眼里都是**文件**；文件夹只是把文件分组，本身不装内容。

**为什么你该在意**：因为 agent 干活的方式，本质就是**读文件、改文件、跑文件**。它说"我改好了"，实际含义永远是"磁盘上某个文件的字节变了"。理解了这一点，很多事就好办了：

- **"它说改好了但界面没变"** ⇒ 十有八九是：文件确实改了，但**程序还在用旧的内存副本**（详见 1.3）。
- **"它说验证过了"** ⇒ 先问一句：**验的是哪个文件、用什么手段看的**（详见 4.1）。
- **"回滚"** ⇒ 就是把文件换回改动前的字节。**前提是改动前存过一份**（详见 5.3）。

**这台机器上，文件长什么样**：以我们的项目为例——

| 你看到的 | 它其实是什么 |
|---|---|
| `<工作区>\00-总目录.md` | 一个纯文本文件（Markdown），记录目录结构 |
| `<工作区>\50-tools\launch\启动DSH.lnk` | 一个"快捷方式"，本身不含程序，只指向别处 |
| `C:\Users\<USER>\.dsh\settings.yaml` | DSH 的配置文件（纯文本，可以用记事本打开） |
| `<工作区>\60-ops\logs\dsh-web-2026-09-22.log` | 日志文件：程序自己写的流水账 |

> 💡 **打个比方**：电脑像一个巨大的档案柜——**盘**是抽屉、**文件夹**是档案盒（盒里还能放盒）、**文件**是盒子里真正的那张纸。**路径**就是从抽屉走到那张纸的完整走法。

**两个容易吃亏的点**：
1. **扩展名决定"谁来打开它"**：`.md` 是文本、`.exe` 是可执行程序、`.mjs` 是给 node 跑的脚本（**双击它通常没反应——它需要一个"解释器"来执行**）。Windows 默认**隐藏扩展名**，建议在文件夹选项里打开显示，否则你改了半天名字可能只改了标签。
2. **改文件的人是 agent，但"改的对不对"要你来定**：机器能验编码、能验结构、能跑回归；但"这样改是不是我想要的"只有你能判（见 4.3 末尾）。

`▸ 延伸`：坑 `K6` 路径写法、`K9` 改文件按行号不靠模式匹配 —— 见 「同仓另篇」。

## 1.2 盘符与路径：为什么我总说 `<工作区>`

**一句话**：路径 = "这个文件住在哪"的完整地址，从**盘**开始，一层层写到文件名。

**这台机器只有两件事要记**：

| 盘 | 是什么 | 你会看到它出现在哪 |
|---|---|---|
| `C:` | **系统盘**：Windows 自己住的地方 | `C:\Users\<USER>\.dsh\settings.yaml`（DSH 配置） |
| `F:` | **项目盘**：我们的东西全在这 | `<工作区>\...`（文档 / 脚本 / 项目 / 插件 / 日志） |

**读路径的诀窍：从右往左读。**

```
    F:  \  dss  \  20-docs  \  docs  \  审计  \  00-当前态.md
    │      │        │            │         │            │
    │      │        │            │         │            └── ① 这才是那个文件
    │      │        │            │         └───────────────② 它所在的文件夹
    │      │        │            └─────────────────────────③ 再上一层
    │      │        └──────────────────────────────────────④ 再上一层
    │      └───────────────────────────────────────────────⑤ 项目的根目录
    └──────────────────────────────────────────────────────⑥ 起点：F 盘
```

说人话：**"F 盘 → dss → 20-docs → docs → 审计 → 那个文件"**。
（图 1：路径树）

> 💡 **打个比方**：`F:\照片\2026\旅行\海边.jpg` —— 先找到"海边.jpg"这张图，它在"旅行"盒里，"旅行"在"2026"盒里，在"照片"盒里，在 F 抽屉里。

**三个你一定会遇到的坑**：

1. **两种斜杠不是随便换的**。Windows 用 `\`，很多程序和 agent 的部分工具要求 `/`。
   同一个文件写 `<工作区>\20-docs` 和 `<工作区>/20-docs` 通常都对；**但文件工具（读/写/改）必须用 `F:/`** —— 写成 `<工作区>` 会被解析成 `F:\f\dss`（凭空多一层 `f` 目录，当然找不到）。*（此坑本轮实测再次印证。）*
2. **路径里有空格或中文时要加引号**，否则命令会把它切成两半。
3. **同名文件可以在不同文件夹里**：`<工作区>\20-docs\docs\审计\README.md` 和 `<工作区>\20-docs\docs\_归档\审计-2026-09\README.md` 是**两个不同的文件**。只喊"README"必然歧义。**这正是我做备份时会加前缀的原因**（如 `审计-README.md`，见 2026-09-22 的 `60-ops\backup\dupfix-20260922\refs\`）。

**为什么这件事排在最前面**：我们所有"事故"里，有一类就是**路径写错但不报错**——写到了别处、或者备份互相覆盖，等到发现时已经晚了两步。

`▸ 延伸`：坑 `K6`、`B3`（多层反斜杠转义不可靠）。

## 1.3 程序 · 进程 · 端口 · 服务：一句话背后的四件事

**一句话**：**程序**是磁盘上的文件；**进程**是它跑起来之后的"活体"；**端口**是它对外开的门牌号；**服务**是"长期跑着、等你来敲门"的那种进程。

```
  磁盘上的文件                   内存里的活体                 网络上的门
  ┌──────────────┐   双击/命令   ┌──────────────┐   监听    ┌────────────┐
  │ node.exe     │ ───────────▶ │  进程 (PID)  │ ────────▶ │ 端口 3080  │
  │ bin.js       │               │  看门狗 PID  │           │ 端口 3081  │
  └──────────────┘               └──────────────┘           └────────────┘
       静态                            动态                      可访问
```

（图 2：程序 → 进程 → 端口）

**为什么 agent 老提"3080""3081"**：

| 说法 | 含义 |
|---|---|
| `3080` | **主机**上 DSH Web GUI 的端口 → 你平时用的这个界面 |
| `3081` | **虚拟机**（Ubuntu-DSH）里 DSH 的端口（VirtualBox 做了 NAT 转发，所以在主机上也能开 `127.0.0.1:3081`） |
| "服务在听" | 端口上有进程在监听 ⇒ 你可以连上 |
| "进程在跑" | 有个活体在内存里 ⇒ 它在工作（但**不代表它在推进任务**） |

**三条实际推论（我们天天用）**：

1. **"文件改了"≠"程序知道"**。程序启动时把配置/插件读进内存；你改了磁盘上的文件，它可能还按旧的跑。
   ⇒ 这就是为什么我们反复出现"**改完要下一个新 turn 才生效**"（记忆配置）和"**有些改动必须重启**"（插件）。
2. **停服务 ≠ 杀进程**。我们铁律是**停服/启服由你手动**（`dsh.cmd stop/start`），agent 的脚本**只准检测端口、绝不 kill 进程**——因为"看门狗式"的自动重启会让 agent 分不清"是我弄崩的"还是"它本来就崩"。
3. **"在跑"≠"在推进"**。判断一个后台任务是否真在干活，要看**产物的变化**（文件大小/时间、日志新增、数据量），而不是"进程还在"。我们真实教训：`-Include` 静默返回空被当成"检查通过"（假绿），以及长任务"看起来在跑"其实卡住。

> 💡 **打个比方**：**程序**=菜谱（放在书架上）；**进程**=正在厨房做菜的厨师；**端口**=出菜窗口的编号；**服务**=一直营业的餐馆（不是做一顿就关门的家厨）。

`▸ 延伸`：坑 `K4`（判据过窄 ⇒ 恒判"无监听"）、`K5`（`stop` 不杀代理 ⇒ 误判"仍在运行"）、`J6`（后台在跑 ≠ 在推进）。

## 1.4 双击得动的与双击不动的

**一句话**：能不能双击运行，取决于**这个文件是"程序本体"还是"需要别人来解释的文本"**。

| 你看到的 | 双击会怎样 | 本质 |
|---|---|---|
| `.exe` | ✅ 跑起来 | **程序本体**（机器指令） |
| `.lnk` | ✅ 跑起来（指向的那个程序） | **快捷方式**，本身不含程序（见 1.5） |
| `.cmd` / `.bat` | ✅ 跑（弹一个黑窗口） | **交给 cmd 解释执行**的脚本 |
| `.mjs` / `.js` / `.py` | ❌ **通常没反应或一闪而过** | **需要"解释器"**（node / python）来执行 |
| `.md` / `.json` | 打开编辑器（那是"看"，不是"跑"） | 文本数据 |

**三条实际推论**：

1. **"双击没反应"≠"文件坏了"**——多半只是**没有解释器在管它**。要让 `.mjs` 跑起来，正确姿势是：
   ```
   node <工作区>/scripts/verify-utf8.mjs <工作区>/20-docs/docs/审计/00-当前态.md
   ```
   （`node` 是解释器，后面跟的是"要它跑的文件"——这就是 3.1 说的"命令行"。）
2. **`.cmd` 双击会弹黑窗口，出错时窗口可能一闪就关** ⇒ **看不到错误信息**。所以排错时不要双击，要在命令行里跑（错误信息才会留在屏幕上）。
3. **双击时的工作目录 = 该文件所在的文件夹**，而命令行里跑时工作目录 = 你当前所在目录。**脚本里的相对路径会因此不同** —— 这是"双击能跑、命令行跑不了"（或反之）的常见原因。

> 💡 **打个比方**：`.exe` 像**自带发动机的车**；`.mjs` 像**一张乐谱**——乐谱本身不会响，得有乐手（`node`）来演奏。双击乐谱当然没声音。

`▸ 延伸`：坑 `A3`（不要用 stdin 喂交互式 `.cmd`）、`K14`（`.cmd` 存成 LF ⇒ cmd 把行碎片当命令）。

## 1.5 junction 与 .lnk：两种"快捷方式"

**一句话**：`.lnk` 是**图形层的快捷方式**（给人点的）；**junction** 是**文件系统层的"传送门"**（给所有程序用的，路径照旧可用）。

```
        .lnk（文件级）                      junction（目录级）
   ┌──────────────┐                    ┌──────────────┐
   │ 启动DSH.lnk  │ ──▶ 目标程序        │ dsh-runtime\ │ ══▶ 10-runtime\dsh\
   └──────────────┘                    └──────────────┘
   谁认：资源管理器/命令行 start       谁认：**所有程序**（对文件系统透明）
   删它：只删快捷方式                  删它：**只能 rmdir**（del /s 会删进真身）
```

（图 4：两种"快捷方式"的本质差别）

**为什么我们非用 junction 不可**：搬迁把目录从旧路径（`<工作区>\dsh-runtime`）移到了新位置（`10-runtime\dsh`），但**代码里 20+ 处硬编码着旧路径**。junction 让**旧路径原样可用**，于是**零改代码、可逆（删链接即回原状）**。这是"用文件系统解决配置问题"的典型手法。

**怎么认出它**：目录属性会显示 `<JUNCTION>`；命令行里可以看目标：
```powershell
Get-Item <工作区>\dsh-runtime | Select-Object LinkType, Target
```

**⚠️ 唯一必须记住的风险**：**删除 junction 只能用 `rmdir`（或 `.NET Directory.Delete`）**，**绝不能用 `del /s`** —— 后者会**顺着传送门走进去，把真身里的文件删掉**。
我们 2026-09-21 已安全删过一个孤儿 junction，验证过"真身 10 文件 / 174K 未变"。

> 💡 **打个比方**：`.lnk` 像**门上的便利贴**（写着"东西在隔壁"）；junction 像**任意门**——你穿过去就真的到了隔壁房间。**烧便利贴没事，往任意门里扔炸弹会炸掉隔壁。**

**当前状态**：`<工作区>` 顶层共 **14 个** junction（完整地图与红线见 「同仓另篇」 §3）。

`▸ 延伸`：坑 `H8`（插件装配三件事：junction / presets 一级目录 / 装完必重启）、`H5`（pnpm `file:` 依赖不刷新）。

# 第二部分 · 文本、编码与"看不见的字符"

> 这一章是**最容易毁东西**的一章：下面三个东西你都**看不见**，但它们能让"看起来一样的文件"彻底坏掉。

## 2.1 文本与编码：同样的字，两种存法

**一句话**：文字在磁盘上不是"字"，是**一串数字**；编码就是"数字 ↔ 字"的对照表。**用错表，读出来就是乱码。**

**这台机器上的现状**：

| 场景 | 该用什么 | 为什么 |
|---|---|---|
| `.md` / `.json` / `.mjs` / 网页 | **UTF-8（无 BOM）** | 国际通用；项目规范 |
| `.cmd` / `.bat`（老式批处理） | **GBK** + `chcp 936` | 中文 Windows 的 cmd 默认按 GBK 读；用 UTF-8 会出现 `'??' is not recognized` |

**两个真实后果**：

1. **乱码只是"看得见"的坏**。更坏的是**看不见的坏**：编码写错时，某些字节组合会被系统**静默替换**（变成 `?` 或 U+FFFD ），**原文永久损毁，改回来也没用**。所以我们把"编码用错"列为**永久损毁类**风险。
2. **node 能读 GBK，但不能写** GBK。所以我们写 GBK 文件一律走 PowerShell 的 `[IO.File]::WriteAllText(..., Encoding(936))`。

**怎么确认没弄坏（这条你要会用）**：项目自带校验器，一条命令看全部：

```
node <工作区>/scripts/verify-utf8.mjs <工作区>/20-docs/docs/审计/00-当前态.md
```

它会**全文严格解码**（不是抽样）并报告：字节数 / 字符数 / 是否有 BOM。为什么需要它？因为某些工具的 UTF-8 检查是**按 64KB 切片**解码的，切点落在汉字中间就会**误报**——这个工作区 2026-09-21 实测复现过两次。

> 💡 **打个比方**：编码就是**翻译规则**。同一串数字，按"英语词典"念是一种意思，按"法语词典"念是另一种；而且**念错还可能把那页纸撕坏**（静默替换）。

`▸ 延伸`：坑 `C1`（node 可读 GBK）、`C2`（写 GBK 走 pwsh）、`K7`（编码用错 = 永久损毁，只 grep `???` 会漏）。

## 2.2 BOM：开头三个看不见的字节

**一句话**：BOM 是文件最开头三个字节 `EF BB BF`，作用是"标记这是 UTF-8"；但**很多程序不认它，会直接报错**。

**我们铁律**：`.md` / `.json` / `.mjs` **一律无 BOM**。判断方法（看开头三个字节）：

```
# 无 BOM（正常）：开头直接是内容
23 20 ...
#  ↑ "# " 的字节

# 有 BOM（要修）：
EF BB BF 23 20 ...
```

**为什么这个坑很阴**：BOM 在记事本/编辑器里**完全看不见**（不会显示成字符），但 JSON 解析器会在第一个字符就失败，报出让你一头雾水的错。我们 2026-09-19 有一条真实记录：**74 号草案文档里的键路径写错**，照它执行会"以为冻住了其实没冻"——同类问题的特征是**表面无异常、实际没生效**。

**一句话记住**：**新建/保存这些文件时，选"UTF-8"而不是"UTF-8 with BOM"**（Windows 记事本老版本默认会加 BOM，这就是坑源）。

> 💡 **打个比方**：BOM 像**在信封里塞了一张"此信为英文"的小纸条**。人读信不在乎；但**机器分拣员**如果只认"信纸第一行是地址"，它会把这小纸条当成地址，然后报"地址格式错误"。

`▸ 延伸`：坑 `K8`（JSON 禁带 BOM；`.ps1` 无 BOM 会被按 GBK 读）。

## 2.3 换行：CRLF 与 LF

**一句话**：一行结束要"换行"，Windows 用**两个字符** `CRLF`（回车+换行，`\r\n`），Linux/macOS 用**一个** `LF`（`\n`）。**用错地方，老程序会把一行碎成好几段命令。**

**这台机器上的规矩**：

| 文件类型 | 换行 | 理由 |
|---|---|---|
| `.cmd` / `.bat` | **必须 CRLF** | cmd 解析器认 `\r\n`；存成 LF 会把**行碎片当命令**执行（我们真实踩过） |
| `.md` / `.json` / `.mjs` | LF | 现代工具都认，且跨平台一致 |

**为什么危险**：`.cmd` 存成 LF 时，cmd 会把**半行**当成一条命令去执行——报错莫名其妙，甚至**执行了半截危险操作**。

**怎么查**：项目校验器会同时报告 `crlf` 与 `bareLF` 计数（例如某文件"CRLF=6 / bareLF=0"就是对的）。

> 💡 **打个比方**：换行就像**句号**。Windows 认为要**两个符号**（句号+空格）才算一句结束；Linux 认为一个句号就够。你把"两个符号"的规则写成"一个符号"给 Windows 看，它会以为两个句子黏在一起，读串行。

**图 3：同一行 `abc` 的三种存法（差异你完全看不见）**

```
UTF-8 无 BOM + LF    : 61 62 63 0A
UTF-8 有 BOM + LF    : EF BB BF 61 62 63 0A    ← 开头多 3 字节（2.2 的坑）
UTF-8 无 BOM + CRLF  : 61 62 63 0D 0A          ← 行尾多 1 字节（本节的坑）
```

（三者在记事本里**长得一模一样**；差别只在字节层面。这就是为什么"看起来没变"不能作为"没弄坏"的证据。）

`▸ 延伸`：坑 `K14`（`.bat/.cmd` 存成 LF ⇒ cmd 把行碎片当命令）、`B4`（MSYS 的 `iconv | sed` 管道会**悄悄吞掉 `\r`** —— 这就是改 GBK 文本必须走 pwsh 的原因）。

## 2.4 怎么确认"没弄坏"：三类校验，各管各的

**一句话**：**"看起来一样"永远不算证据**（图 3 已说明）；要拿出**机器能复核**的判断，共有三类手段。

| # | 手段 | 命令（本机） | 回答什么问题 |
|---|---|---|---|
| 1 | **编码校验** | `node <工作区>/scripts/verify-utf8.mjs <文件...>` | 这文件**是不是合法 UTF-8**、有没有 BOM、有没有坏字符 |
| 2 | **哈希对拍** | `Get-FileHash -Algorithm SHA256 <文件>` | **两份东西是不是真的逐字节一样**；文件**有没有被改过** |
| 3 | **回读断言** | 改完**再读回来**，检查目标字段/行是否真变了 | "我改了"**真的落盘了吗**（对付"假成功"） |

**为什么三类都要有**（各有盲区）：

- 编码校验**看不出内容对错**——它只说"字节合法"。
- 哈希**看不出"该不该改"**——它只说"变了/没变"。⚠️ 特别注意：**哈希只能证明"不同"，不能用来当"逐字节相同"的长期承诺**（东西一改，之前写下的哈希就成了假话，见 2.5）。
- 回读断言**看不出"整体是否协调"**——它只证明你查的那一处。

**额外的第一眼检查（BOM，30 秒）**：
```powershell
$b = [System.IO.File]::ReadAllBytes('<工作区>\20-docs\docs\README.md')
'{0:X2} {1:X2} {2:X2}' -f $b[0], $b[1], $b[2]     # 开头若是 EF BB BF 就是有 BOM（.md/.json/.mjs 不要）
```

**我们实际怎么用**：改完文档 ⇒ 跑 `verify-utf8`（编码）+ `verify-refs`（文档里引用的文件是否还存在）；改完代码 ⇒ 语法检查（`node --check`）+ 跑一遍；**改前先留备份** ⇒ 哈希对拍能证明"备份和原件不一样/一样"。

> 💡 **打个比方**：编码校验 = **看这份文件"有没有错别字到读不通"**；哈希 = **指纹比对**（是不是同一个人）；回读 = **写完信拆开再念一遍**（确认真写进去了）。三件事互不替代。

`▸ 延伸`：坑 `C1`/`C2`（GBK 读写的分工）、`K7`（编码用错 = 永久损毁）、`E2`（别把错误也吞掉）。

## 2.5 文档里的"活的假话"：一个真实案例

**一句话**：**文档写下的"事实"会过期，而过期的事实比没有更危险**——因为它会被当成真的照着做。

**案例（2026-09-22 实测，就在我们）**：某份交接文档写着：

> "`事故\25-…md` 与归档的 `交接文档-20260910.md` 是**逐字节相同**的同源副本（sha256 `5682215150…`）⇒ **改一份必须同步另一份**。"

**真相**：那份哈希**写下时是真的**（2026-09-20 核对过）；但此后**两份被分别编辑**，到 09-22 已经**13 处措辞不同、字节数差 266**。于是这句声明变成了**活的假话**：照它干活的人会以为"改一处就够"或"两处总是一致"。

**它还散在 6 个地方**（两份文件内部 + 两个 README + 清单 + 结题总结），所以你**改一处也修不干净**。

**处置（已做）**：**归一为一份**——归档件改成**指针壳**，**唯一真相源 = `事故\25-…md`**，并把 6 处引用全部更正。

**三条可迁移的经验**：

1. **别写"人工同步约定"**（"改 A 要记得同步 B"）——它**必然失效**，因为人的记忆和纪律都会断。**要么只保留一份，要么让另一份只留指针。**
2. **凡是"事实型"声明都带日期与来源**（"2026-09-22 实测"），这样过期时**一眼能看出该重核**。
3. **发现假话要显式更正并说明原因**（不是偷偷改掉）——我们规矩：**推翻旧结论必须写"取代 20XX-XX-XX 的 XXX"**。

> 💡 **打个比方**：文档里的过时事实，像**冰箱里那盒忘了多久的剩菜**——它看起来还在，但吃了会出事。定期清理（时效声明 + 索引核对）比"闻一下觉得没事"可靠。

`▸ 延伸`：我们另有同类实例——`76` 号自称"待你拍板"而其实 09-16 就执行完了（2026-09-22 已更正索引）；归档目录统一加"时效声明"的做法见 「同仓另篇」 §维护规则。

# 第三部分 · 命令行：为什么 agent 用它、你怎么看懂

## 3.1 命令行是什么：一句话下指令

**一句话**：命令行就是**用打字代替点击**来指挥电脑。绝大多数图形界面做的事，命令行都能做，而且**可复制、可重复、可留痕**。

**为什么 agent 偏爱它**：三个理由，都很实际——

1. **可留痕**：agent 执行了什么，命令本身就是证据（"我跑了这个，输出是这个"）。点鼠标无法留痕。
2. **可重复**：同一条命令换个文件名就能再来一遍（例如给 9 个文档跑编码校验）。
3. **快**：一次命令顶十几次点击；批量处理时差距是**十倍级**。

**代价是什么**：命令行**不会可怜你**——写错一个字符，它不会跳出来问"你是不是想删这个？"，它会**照做**。所以第 3.3 节的护栏很关键。

> 💡 **打个比方**：图形界面像**点菜**（菜单上没有的做不了，但你不会点错）；命令行像**直接跟厨师报配料**（什么都能做，但说错了他也照做）。

`▸ 延伸`：坑 `A3`（不要用 stdin 喂交互式 `.cmd` —— 会卡死等输入）、`E4`（长任务先 `--dry-run`）。

---

## 3.2 两个壳：Git Bash 与 PowerShell

**一句话**：**壳（shell）**是"你打命令、它去执行"的那一层程序。本机有**两个**常用壳，**各有擅长**，agent 会**按任务选**，不是选了一个就不换。

| 壳 | 本机位置 | 擅长 | 短板 |
|---|---|---|---|
| **Git Bash**（MSYS） | 随 Git 安装 | 文本处理、`grep`/`find`/`sed`、路径简单、启动快 | 反斜杠转义不可靠；改 GBK 文本会吞 `\r` |
| **PowerShell** | 系统自带 **5.1** + 已装 **7.6.6** | 注册表、**`[System.IO.File]` 等 .NET 类型**、Windows 系统接口 | 启动慢；5.1 与 7 语法有差异 |

**这里有个本机专属的坑，必须记住**：

> **agent 的工具默认走 PowerShell 5.1**（不是 7.6.6）。
> 后果：**无 BOM 的 UTF-8 `.ps1` 里如果有中文，会被 5.1 按 GBK 解析而失败**。
> 两个解法：给 `.ps1` 加 BOM，或**改走 node**。
> 需要 PowerShell 7 时：**在 Git Bash 里调 `pwsh` 就行**（实测可行）。

**还有一个反直觉点**：`pwsh` 这个名字容易骗人——它既可能是 PowerShell 7 的命令名，也可能是"随便一个 PowerShell"。我们实测结论是：**工具走 5.1，但经 bash 可以直接用 7**。

> 💡 **打个比方**：两个壳像**两把螺丝刀**：一把十字、一把一字。你不会问"哪把更好"，你问"这颗螺丝是哪种头"。

`▸ 延伸`：坑 `B1`（`cmd //c` vs `cmd /c`：MSYS 路径转换）、`K17`（`pwsh` 这个名字会骗人）、`K11`（cmd/PowerShell 的参数与内置命令坑）。

---

## 3.3 危险命令与护栏：为什么危险

**一句话**：命令行里最危险的不是"删除"，而是**"删除 + 通配符 + 路径写错"**这三件事凑在一起。

**我们最硬的一条红线**（务必记住）：

| 命令 | 后果 |
|---|---|
| `rmdir <工作区>\dsh-meme`（删 junction） | ✅ **只删链接**，真身 `40-plugins\dsh-meme` 完好 |
| `del /s <工作区>\dsh-meme\*` | ❌ **顺着链接删进真身**——真文件全没 |

**为什么**：`<工作区>\dsh-*` 这几个是 **junction（目录联接）**——长得像文件夹，其实是"传送门"。删除链接和删除门后的房间是**两件事**，而 `del /s` 会走进去删。

**四条通用护栏（agent 也被要求遵守）**：

1. **先 `--dry-run`**：脚本/操作**先预演**，看它打算改什么，再真跑。我们三次事故同源（"脚本看着对"）。
2. **危险命令不用 shell 变量**：`rm -rf $VAR/x` 在长命令链里变量丢失 ⇒ 变量为空 ⇒ 变成了"从根目录删"。我们真实踩过（幸好没权限）。
3. **不可逆操作先问**：删除、覆盖、停服、改配置——**动手前必须先问**（见 4.3）。
4. **改文件按行号、不靠模式匹配**：模式匹配会"匹配到别处"（我们有名案例：读 JSON 时把 `keep` 当成 `keepTag`，误删 1 条，靠备份恢复）。

> 💡 **打个比方**：`del /s` 走 junction，就像**你以为在撕一张便签，实际撕的是便签上写的那个房间里所有东西**。

`▸ 延伸`：坑 `B2`（危险命令不要用 shell 变量）、`E1`（读 JSON 前必须确认字段名）、`E4`（先 dry-run 再 apply）、`K9`。

## 3.4 读命令的三步法：程序 + 参数 + 路径

**一句话**：任何一条命令行，都能拆成 **① 用哪个程序 ② 给它什么开关 ③ 对哪个东西下手**。学会这三步，**陌生的命令你也能看懂大概**。

**第一步：程序**（这行第一个词）——它决定"谁来干活"。

| 你看到的首词 | 是什么 |
|---|---|
| `node` | 用 Node.js 解释器跑一个 `.mjs`/`.js` 脚本 |
| `Get-FileHash` / `Select-String` / `New-Item` | PowerShell 内置命令（动词-名词结构） |
| `ls` / `grep` / `sed` / `rm` | Git Bash（Linux 风格）里的工具 |
| `C:\...` 或 `& '路径'` | 直接调用某个 `.exe`（路径有空格时要加引号，PowerShell 里前面加 `&`） |

**第二步：参数**（以 `-` 或 `--` 开头的部分）——它们**改变行为**，不改变"对谁下手"。
**第三步：路径**（剩下的部分）——"对哪个文件/目录/对象下手"。

### 五条真实命令的拆解

**① 编码校验**
```
node <工作区>/scripts/verify-utf8.mjs <工作区>/20-docs/docs/审计/00-当前态.md
└┬─┘ └────────── 参数？不，这是"要跑哪个脚本" ──────────┘ └──── 路径：校验谁 ────┘
 node            verify-utf8.mjs（脚本本身也是一个路径参数）
```
读法：**用 node 跑 verify-utf8 这个脚本，让它校验 当前态文档 这个文件**。

**② 查记忆写入开关状态**
```
node <工作区>/scripts/mnemon-write-switch.mjs status
                                             └─┬──┘
                                              参数：要它做"查状态"这件事（不是路径）
```
读法：**同一个脚本，换一个"动作参数"就干另一件事**（`on` / `off` / `status`）——这是脚本设计的常见做法。

**③ 算哈希（PowerShell）**
```
Get-FileHash -Algorithm SHA256 '<工作区>\20-docs\docs\README.md'
└────┬─────┘ └────┬─────┘ └──┬──┘ └──────── 路径（含空格/特殊字符要引号）────────┘
     程序        参数：算法   参数值
```
读法：**用 Get-FileHash 这个命令，指定算法 SHA256，对这份文件算指纹**。

**④ 进虚拟机干活（我们常用）**
```
& '<VBox 目录>\VBoxManage.exe' guestcontrol Ubuntu-DSH run --exe /bin/bash --username <VMUSER> --password *** --wait-stdout -- -c '要执行的命令'
└──────────┬──────────────┘ └────┬────┘ └──┬───┘ └────────── 一串参数 ──────────┘ └─┬─┘
   程序（& 表示"直接调这个 exe"）  VBox 子命令  虚拟机名                            分隔符 → 后面的都是"在 VM 里执行的命令"
```
读法：**让 VBoxManage 以 guestcontrol 方式，在 `Ubuntu-DSH` 这台虚拟机里，用 bash 跑我给的命令**。
⚠️ 两个坑：路径**含空格必须引号**；`--` 是**分隔符**，它之前是"给 VBoxManage 的参数"，之后才是"给 VM 的命令"。

**⑤ 启动 DSH（你日常用的那条）**
```
node <工作区>\dsh-runtime\node_modules\@deepseek-ai\dsh\lib\bin.js web --port 3080
└┬─┘ └──────────────────── 路径：DSH 的入口脚本 ────────────────────┘ └┬─┘ └───┬───┘
node                                                                 子命令  参数：端口
```
读法：**用 node 跑 DSH 的入口脚本，进入 `web` 模式，监听 3080 端口**。
（实际使用中你双击 `dsh.cmd start/stop/restart` 就行，不必手敲这条——这里只是让你看懂它。）

### 遇到陌生命令时的三步自问

1. **第一个词是什么？**（程序 / 内置命令 / 脚本路径）
2. **带 `-` 的那些词在改什么行为？**（不算全懂也没关系，看关键词：`dry-run`=预演、`--force`=强制、`-Algorithm`=算法）
3. **最后一个（或几个）路径是"对谁下手"？** —— ⚠️ **这一步最关键**：**看错目标，前面全对也会干错事**（3.3 的 `del /s` 就是典型）。

> 💡 **打个比方**：命令像**快递单**——**寄件方式**（程序）+ **备注选项**（参数）+ **收件地址**（路径）。看不懂备注没关系，**地址看错就是寄错人**。

`▸ 延伸`：坑 `K11`（cmd/PowerShell 的参数与内置命令坑）、`B1`（`cmd //c` vs `cmd /c`）。

## 3.5 后台任务与日志：怎么知道"它真在干活"

**一句话**：跑得久的活要**放后台**（否则前台一直等，看着像卡死）；判断"是否真在推进"，**只认产物与日志**，不认"进程还在"。

**三条实用判据**（我们反复用到）：

| 判据 | 怎么看 | 说明 |
|---|---|---|
| **产物在变** | 文件大小 / 修改时间在动 | 最硬的证据 |
| **日志在增** | `<工作区>\60-ops\logs\` 里对应日志**新增了行** | 日志按天落在工作区的 logs 目录（示例见 1.1） |
| **数据量在涨** | 处理条数 / 字节数递增 | 适合批量任务 |

**⚠️ 反面判据（看着像"在跑"其实没动）**：
- 进程存在（可能已卡在等输入、等锁、等网络）
- 界面显示"正在处理"（前端可能只是没刷新）
- 屏幕上没报错（**没日志 ≠ 没错误**）

**我们三个真实教训**：

1. **不要用 stdin 喂交互式脚本**：某次用管道模拟交互式 `.cmd` 的菜单输入，脚本在 `pause` 处**卡满 5 分钟** ⇒ 正确做法是"只加载菜单就退出"的非交互冒烟。
2. **长任务放后台**：3.28 MB 会话的 dry-run 放前台等，直接超时 ⇒ 改 `run_in_background`，期间继续做别的事。
3. **看清"是谁慢"**：报错先分清 **shell 慢** 还是 **被调用的程序慢**（例如 node 解压 zstd 慢，与 shell 无关）。
   另有一条本机边界：受限模式下，程序**无法用管道捕获另一个程序的输出**（会报 `EPERM`）——**这是沙箱规则，不是命令写错**（遇到就换方式或按文档升级一次权限，**别绕**）。

**怎么要求 agent 干长活**（一句话模板）：
> "这个任务预计很久 ⇒ 放后台跑；**每完成一段给我可验证的进度**：产物路径 + 大小 + 关键数字。"

（"它在跑不是证据"的完整讨论见 `03-discipline-of-pairing-with-ai.md` §6。）

> 💡 **打个比方**：判断"洗衣机在洗"不能靠**听见嗡嗡声**（进程还在），要看**桶里水在转**（产物在变）。噪音可能是它在空转。

`▸ 延伸`：坑 `J6`（后台在跑 ≠ 在推进）、`J7`（"消息已发送"是假验证）、`A3`（stdin 喂交互式脚本）。

# 第四部分 · 跟 AI 协作（本文真正的重点）

## 4.1 什么叫"验证过"

**一句话**："验证过"不是"我看了一遍觉得对"，而是**拿出别人能复核的证据**。我们的规矩是：**证据分四种，缺哪种补哪种。**

| # | 证据形态 | 长什么样 | 能证明什么 |
|---|---|---|---|
| 1 | **文件** | 产物路径 + 大小 + 编码（UTF-8 无 BOM） | 东西确实生成了，不是口头承诺 |
| 2 | **命令输出** | 真实 stdout 摘要（如 `passed=true / failures=0`） | 机器检查真的跑过 |
| 3 | **截图（且人要真看）** | 页面/界面截图 + **人工复核** | 视觉结果正确（**没看过的截图不算证据**） |
| 4 | **断言** | `grep` 命中/未命中、DOM 计算值、哈希对比 | 特定事实为真/为假 |

**为什么"截图没看"不算数**：我们明确写过——**视觉类证据必须被"真的看一遍"**（机器截了图但没人看，等于没验）。

**一条实用判据**：**凡是"它说好了"，你都可以问三个问题**——
1. **验的是哪个文件/哪个页面？**（对象）
2. **用什么手段验的？**（方法：跑命令？读回？截图？）
3. **反例是什么？**（如果这事是错的，会看到什么？——**想不出反例的验证通常是假验证**）

> 💡 **打个比方**：体检报告 ≠ "我感觉挺好"。抽血化验（机器证据）+ 医生看片（人看证据）**两样都要**。

`▸ 延伸`：坑 `J7`（"消息已发送"是假验证）、`K3`（守卫必须双向断言，"保命组件"必须真跑一次）。

## 4.2 假成功与假失败

**一句话**：机器给的"成功/失败"经常是错的——**成功的可能是空跑，失败的可能是误报**。下面六个都是我们真实发生过的。

**假成功（说好了，其实没做）**：

| 现象 | 真相 |
|---|---|
| `Get-ChildItem -Include` 返回空，被判"无残留" | **参数用法不对 ⇒ 静默返回空**，等于没查 |
| "消息已发送"（检查 `innerText` 有内容） | 输入框有字 ≠ 消息进了会话（判据错了） |
| `cp -a` 备份后"备份都在" | 备份目录的 **mtime 继承源目录** ⇒ 排序错乱 ⇒ 脚本删掉了**最新那份** |

**假失败（说坏了，其实没事）**：

| 现象 | 真相 |
|---|---|
| 大文件报 `not valid for encoding utf-8` | 检查器**按 64KB 切片**解码，切点落在汉字中间 ⇒ **文件其实是好的** |
| `git` 报"会话数据损坏" | 工具**误报**（漏了持久化层解码）⇒ 全库 444 个会话实测 **PASS 444 / FAIL 0** |
| 长会话报 `seq gap` | 运行中的 headless 会话**属预期**，不是损坏 |

**你要建立的直觉**：**"报错先分清是谁在报错"**——是程序真错了、是工具口径不对、还是**检查方法本身有问题**。我们专门为最后一种造了两个校验器（`verify-utf8.mjs` / `verify-refs.mjs`），就是因为"**误报比不报更费时间**"。

> 💡 **打个比方**：体温计坏了，你会一会儿以为自己发烧（假失败）、一会儿以为没事（假成功）。**先校准工具，再信读数。**

`▸ 延伸`：坑 `K10`（`-Include` 静默返回空 = 假绿）、`I6`（判"损坏"的工具本身会误报）、`E2`（输出重定向别把错误也吞掉）。

## 4.3 什么时候必须叫停

**一句话**：**凡是"退不回去"的操作，动手前必须先问**——这不是不信任 AI，而是**风险不对称**：做对了收益有限，做错了代价很大。

**我们红线的底层逻辑（不是拍脑袋定的）**：

| 红线 | 底层理由 |
|---|---|
| **停服/启服由你手动**（`dsh.cmd stop/start`）；agent 只准检测端口 | agent 自己就在这个服务里跑——**它 kill 服务等于自杀**，还会让"为什么崩"无法归因 |
| **删 junction 只能 `rmdir`** | `del /s` 会删进真身（3.3 已讲） |
| **改热记忆走"开锁 → 新 turn → 改 → 关锁 + 同步 staging"** | 记忆有"每轮注入"和"开机合并"两套机制，**绕流程直接改会被回滚** |
| **高风险改动走 VM 评审** | 进程/端口/文件移动/编码敏感/守卫类脚本 —— 出错的代价不可逆 |
| **`.cmd` 一律纯 ASCII** | 绕开 GBK/CRLF/`chcp` 三重编码坑（一次踩够） |

**一句可操作的判据**：动手前问自己 —— **"如果没有备份，这一步做错了还能回去吗？"**
不能 ⇒ **先备份，或先问**。我们今天（2026-09-22）改一份文档前，就先做了两组冷备（原始字节 + 改动前引用件），所以"归一份档"这种改动**随时可退**。

**最后一条，也是最重要的一条**：**机器验不了"品味"**。
"这段剧情合理吗""这个选择有没有分量""这样写会不会出戏"——**只有你能判**。
分工应当是：**机器管回归与硬伤（编码、锚点、数值越界），你管品味**；而**别让 AI 用"能跑就算过"糊弄你**（这是我们明确记录过的通病）。

> 💡 **打个比方**：手术可以做（有把握），但**术前同意书必须你签**。签的不是"我不信医生"，而是"我知道切掉的是哪块、有没有留后路"。

`▸ 延伸`：坑 `K1`–`K3`（探针自指 / 探测失败被当成"确认为否" / 守卫必须双向断言）、`I13`（改活动会话文件前必须停服）。

## 4.4 一次好的委托长什么样：目标 + 判据 + 边界

**一句话**：好委托 = **要什么** + **怎么算做成了** + **不许碰什么**。三样缺一样，返工概率就上一截。

| 要素 | 作用 | 例子 |
|---|---|---|
| **目标** | 说清"做完是什么样" | "把两份重复文档合并成一份" |
| **判据** | 说清"怎么证明做成了" | "引用不能有断链；改完给我校验器输出" |
| **边界** | 说清"哪些不许动" | "**别删**归档件；不确定就先问我" |

**模板（可以直接抄）**：
> 【目标】把 X 变成 Y。
> 【判据】做完给我：① 产物路径 ② 校验命令的输出 ③ 有没有反例。
> 【边界】不许动 A / B；遇到 C 情况先停下来问我。

**为什么"边界"最容易被忽略却最重要**：agent 拿到模糊指令时会**自己补全范围**。你说"顺手清理一下零碎项"，它可能把"看起来没用"的备份也删了。**我们的做法是：动手前先盘点、把清单摆给你看**（本轮就是这么做的——先列 8 项现状，再分"真待办 / 已闭环 / 需你拍板"三类）。

**你这轮的三次委托，正好三种典型**：
- 「**读交接文档**」= 目标清楚、范围明确 ⇒ agent 顺手核了 3 处声明，还发现 1 处假声明（**超额交付来自"顺带核验"，值得鼓励**）。
- 「**先 4 再 3 最后 2**」= 只给了**顺序**，没给范围 ⇒ agent 需要自己界定"零碎项"包含什么（**这种时候让它先出清单最稳**）。
- 「**先出大纲 + 一节样例给您选**」= **把决策点前移**的委托方式 ⇒ 你在低成本阶段就能纠偏，避免写完 25 页才发现方向不对。**这是最高效的委托形态。**

> 💡 **打个比方**：委托像**装修交底**——"我想要亮堂的客厅"（目标）+"验收时白天不开灯也要看清字"（判据）+"承重墙不许动"（边界）。少说哪一条，返工都算你的。

`▸ 延伸`：坑 `E4`（先 dry-run）；"评审只指事前决策"见 `03-discipline-of-pairing-with-ai.md` §1。

## 4.5 为什么"写下来"比"记住"可靠

**一句话**：**会话会结束、上下文会丢、模型会忘**——只有**落成文件**的东西能跨过下一轮。

**我们的三层做法**（事实地图见 「同仓另篇」 §4）：

| 层 | 记什么 | 谁在用 |
|---|---|---|
| **当前态文档**（`审计\00-当前态.md`） | **活跃任务线 / 阻塞 / 待拍板 / 最近交接** | **每轮开工先读、收工写回**（滚动覆盖） |
| **手册**（`手册\NN-…md`） | **权威长文**：流程、纪律、教训、地图 | 需要细则时查 |
| **记忆空间** | 按主题召回的**细则** | agent 按需检索 |

**这套东西解决的真实问题**（你已见过多次）：
- 上一会话在"卡在账本重建"处结束 ⇒ 新会话**读 当前态文档 + 交接**就能接上，不用你重讲一遍；
- 有些坑踩过两次以上 ⇒ 收进避坑手册（同仓另篇）**下次直接查**；
- 有些事实（机器配置、端口口径）每轮都要用 ⇒ 收进热记忆**每轮自动带上**。

**给你的实用建议**：
1. **让 agent"落成文件"**：重要的结论、方案、决策，都说"**写进文档并给我路径**"——比让它"记住"可靠得多。
2. **长内容存文件当纪念品**：你个人的长文/复盘/语录，我们一贯做法是**存成文件**（如 `_归档\analysis-*\` 的历次结题包），而不是塞进记忆系统——**记忆只放"指针"**。
3. **一件事只有一处权威**：如果同一个事实在两处都写着，**早晚会分叉**（2.5 节的真实案例就是这么来的）。发现重复 ⇒ 合并成一份，另一处留指针。

> 💡 **打个比方**：会话上下文像**白板**（下一节课就擦掉），文档像**笔记本**（能翻回去）。重要的事别只写在白板上。

`▸ 延伸`：本文 §2.5（活的假话）；「同仓另篇」（上下文隔断：怎么让 agent 少读文件）。

## 4.6 你该管的与不该管的

**一句话**：**机器管"对不对"，你管"好不好"**——两者不可互相替代，混了就会两头空。

| | 机器（agent）该管 | 你该管 |
|---|---|---|
| **判据性质** | **客观、可复核**：编码合法 / 引用不断 / 语法通过 / 数值不越界 / 回归不红 | **主观、需品味**：剧情合不合理 / 选择有没有分量 / 会不会出戏 / 好不好玩 |
| **典型问题** | "这个文件是不是合法 UTF-8？" | "这段文字读起来像不像人话？" |
| **为什么** | 机器**测不了品味**（它没有你的审美与上下文） | 你不该做**机械重复**的核对（机器更快更准） |

**我们明确记录过的通病**：**"能运行就过"**——AI 容易把"跑起来了"当成"做对了"。所以你要**主动问那三个问题**（4.1）：**验的是谁？怎么验的？反例是什么？**

**另一条重要分工（来自我们真实教训）**：**别让你做大量随机全量测试**。
正确形态 = **剧本测试**：固定一条路径、聚焦验收点（"你只走这条对话，看这三处是否合理"），而不是"你自己随便玩两小时找 bug"。前者你 5 分钟能给结论，后者又累又低效。

> 💡 **打个比方**：机器是**体检仪**（量血压、拍片子，客观），你是**主刀医生**（判断该不该开刀、开哪儿）。**让体检仪决定手术方案是错的；让医生去手工数血细胞也是错的。**

`▸ 延伸`：两条元规矩（**品味只有你能判**、**别用大团队尺度衡量个人项目**）见 `03-discipline-of-pairing-with-ai.md` §7。

# 附录 A · 一页速查卡

**路径读法**：从右往左读 → 文件 → 它的上级 … → 盘。
**两种斜杠**：文件工具（读/写/改）**必须 `F:/`**；`<工作区>` 会被解析成 `F:\f\dss`。
**编码**：`.md/.json/.mjs` = UTF-8 **无 BOM**；`.cmd/.bat` = **GBK + CRLF**。
**自检三件**：
```
node <工作区>/scripts/verify-utf8.mjs <文件...>      # 编码（全文，非切片）
node <工作区>/scripts/verify-refs.mjs <文件/目录...>   # 文档引用能否打开
Get-FileHash -Algorithm SHA256 <文件>               # 哈希（对拍"是否真的一样"）
```
**两个壳**：Git Bash（文本/快）｜PowerShell（系统/.NET）——**工具默认 5.1**，要 7 就在 bash 里调 `pwsh`。
**危险度排序**：`del /s` 走 junction ≫ 通配符删除 ＞ 覆盖文件 ＞ 新增文件。
**问三个问题**：验的是谁？怎么验的？反例是什么？

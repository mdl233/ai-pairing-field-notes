# 把工作留下来的做法

> 这是 03 纪律篇的操作层。03 讲原则与判据（为什么），本篇讲做法与实测数字（怎么抄）。
> 两篇不重述对方。要"为什么"看 03，要"怎么做、坑在哪"看本篇。
> 数字都来自一台真实机器的实测，当参考值，不是标准答案。
> 时效：复核 2026-10-28。

---

## 0 三种最贵的损失

跟 AI 做长期项目，真正心疼的不是"某次做错"，是这三类留不住。

| 损失 | 长什么样 | 对应 |
|---|---|---|
| 丢结论 | 上次想清楚的东西，这次又问一遍；会话一结束就归零 | §1 记录与接力 |
| 假真相 | 两处写同一件事，其中一处早就不对了，而且看不出来 | §2 真相源 |
| 退不回去 | 删了、覆盖了，回不来；或者以为备份了 | §3 可逆性 |

后面两节：§4 验证怎么做才不算自欺，§5 成本花在哪。

## 1 记录与接力

### 1.1 滚动的当前态（一页纸）

固定一个文件，只记"现在是什么"：活跃任务线、阻塞（卡在哪、等谁）、待决策（要人拍板的）、最近几次交接的指针。

两条纪律：每轮开工先读它，收工写回它；滚动覆盖，不归档。

为什么：接手的人或下一个会话的自己，只需要一页纸就知道从哪继续。历史复盘交给长文档。

### 1.2 变更台账：自己的失误也要记

每次改动落一行：

```
时间戳 · 事件戳（提交号 / 编号） · 落点 · 判据
```

四条写法：只追加不删行；口径变化写"取代 …"；没做的标 ❌；自己的失误单独成节。

为什么：台账的价值不在"证明我做了什么"，在"下次同类问题能查到上次怎么解决的"。而记失误是唯一能防重复犯错的机制。我的台账里专门有一节叫「我自己的失误（这类最该被追责）」。

### 1.3 变更即记账，同轮做

改手册、改文档、改配置、换版本之后，同一轮就写台账。

"回头补"约等于永不补。真实教训：触发点里只写了"改配置、换版本"，漏了"改文档"，一天订正 30 余处却一条没记，直到被问起。

教训：规矩要写进触发点清单，不能靠记性。

### 1.4 交接件与开篇词

一个阶段结束前出一份交接件，包含：现状（实测，不是回忆）、未闭环项、决策留档、给下一轮的建议。再写一份开篇词——一段能整段粘给新会话的第一条消息。

会话会满、上下文会丢。没写下来的，等于没发生过。

### 1.5 过期的东西：标注，不篡改

给过期文档加一个时效声明块（写明哪几条已作废、现行在哪），不改写原文、不删除。

历史件是现场，改它等于篡改证据；但不标它，别人会照着抄。平衡点就是标注不篡改。

### 1.6 状态类数字：带日期，给取数命令

凡"当前状态"类数字（版本号、端口、插件数、文件数、占用大小），必须带日期，并写清这条数字怎么取到的。

不写命令，读者无法自证，只能照抄；抄来的数字一定会过期。

我的实测：同一份配置档案的"已装插件数"一天之内漂了两回（13/12、14/13、15/14），而且每次都是我刚补上的数字。第三次之后改了做法：只留取数命令，不留数字。

触发点：改过配置（装卸组件、升级、改端口）之后，必须重跑一次取数命令，并把结果回写。

推论：写"状态"不如写"怎么查状态"。前者会腐烂，后者不会。

## 2 真相源：让哪句算数一眼可知

### 2.1 留指针，不留副本

真实案例：一份文档和它的副本，两处都写着"逐字节相同，改一份必须同步另一份"。

写下时是真的，之后两份被分别编辑，核对时已有 13 处措辞不同。于是那句声明成了活的假话，而且散在 6 个地方（两份文件内部、两个索引、一个清单、一份总结）。

做法：归一为一份，其余只留指针。永远不要写"改 A 记得同步 B"这种人工约定，它必然失效。

### 2.2 判重：看起来重复和真的重复是两件事

先看结构信息（是不是软链、路径、版本、修改时间），再读差异内容，才下结论。

| 现象 | 真相 |
|---|---|
| 重复体检脚本报 1529 组重复 | 排除软链后，真正的重复只剩 7 件。目录联接会让同一份内容在两个路径下各出现一次 |
| 两个同名脚本，哈希不同 | 不是分叉。一个是本机硬编码版，一个是对外通用版，是刻意分工 |

哈希不同不等于分叉。

### 2.3 删除、搬迁之前，先查谁指向它

动手前查全库引用。禁止用"拿完整文件名全文搜索、命中就算有引用"这种土办法——文档里普遍用通配前缀（`*.bak-xxx`、`config.json.bak-*`），完整名匹配必然漏判。

真实反面案例：按"每个目标只留最新一份"清理了 29 个备份，其中 5 类正是文档里写着的回滚点。因为我按文件名理解它们，而文档里记的是通配前缀。

推论：凡"保留最新 N 份、其余删掉"的批量清理，先列出被文档点名的清单再动手；拿不准的一律只报不删。

### 2.4 正本与派生稿：先改上游，再重导

一份内容往往有两个面：正本（自己看的完整版）和派生稿（对外发布或交付的版本）。

发现派生稿有问题时，先改正本，再重新导出。不要直接改派生稿了事。

直接改派生稿等于立刻开始双份维护；而且"正本其实也错"这件事，只有回头改上游才会被发现。我的反例：一天之内两次只改派生稿、没改正本，都是后来才发现的。

三种同步方式要分清：

| 类型 | 同步方式 |
|---|---|
| 可脚本重导（规则化替换） | 改完正本跑一次命令 |
| 需要人工适配（裁章、改写交叉引用） | 人工，列清单逐项对 |
| 汇编稿（事实来自多份正本） | 没有通道，正本一变就人工重核 |

### 2.5 给文档库做体检：四条判据

文档到几百篇之后，索引和磁盘开始对不上，而且不报错，只让后来的人找不到东西。

四条判据（`tools/doc-index-check.mjs` 按这四条做只读检查）：

| # | 判据 | 说明 |
|---|---|---|
| ① | 未登记 | 磁盘上有 `.md`，索引里没有。东西在，等于不在 |
| ② | 悬空 | 索引登记了，文件已经不在了。死链 |
| ③ | 互指 | 目录索引与顶层索引要以路径形式互相提到，只提文件名不算 |
| ④ | 污染 | 脚本产物落进文档目录，该移走 |

再加一条覆盖度纪律：输出必须带"扫到几个、跳过几个（含原因）"。否则那句"0 问题"可能只是"什么都没扫到"。

```bash
node tools/doc-index-check.mjs --root <你的库根> \
  --registry docs/README.md --top-index README.md --docs-dir docs
# 退出码：0 干净 ｜ 1 有告警 ｜ 2 用法错，可直接挂进提交前钩子或 CI
```

这四类问题单看每一处都不像错，但会无声累积，最后表现为"这个库我不敢信"。定期跑一次只读检查，比事后考古便宜。

## 3 可逆性：动手前先问一句

### 3.1 判据

"这一步做错了，退得回来吗？"

退不回去，就先备份、先 dry-run、或先问人。

### 3.2 备份的价值等于"回滚是一条命令"

没有那条命令，改动就只能往前。所以备份要同时给出一条可执行的回滚命令，而不是"我备份过了"。

### 3.3 删除是物理的

实测：这类工具的 `remove` 是直接重写文件，没有墓碑、没有历史版本表。

唯一回滚来源就是外部冷备份，冷备份不是可选项。

配套做法（先写后删 + 双条件验证）：

1. 先把要保留的内容写到别处（另一个层、另一个文件）。
2. 验证真的写进去了，条件有两个：写入回执是"新增"或"更新"，且能拿到目标 id；用该 id 或换一组关键词再查一次，命中同一个 id。
3. 才允许删。

工具报 skipped 时不算证据，它明确要求"另做一次查询才算数"。遇 skipped 禁止删，先改写内容或换个地方。

### 3.4 长任务、批量操作：先 dry-run

先预演看它打算改哪些，再真跑。危险度排序：

```
顺着链接删除 ≫ 通配符删除 ＞ 覆盖文件 ＞ 新增文件
```

## 4 验证：怎么做才不算自欺

> 原则在 03 §2，这里只讲可操作的部分。

### 4.1 判据写成"命令 + 期望值"

坏判据："检查一下有没有问题。"
好判据："跑 `node tools/verify-refs.mjs docs`，期望 0 命中。"

硬指标要能复算。给阈值时同时给来源（哪个公式、哪条实测推出来的）。禁止无出处的数字。

### 4.2 反例：想不出反例的验证，通常是假验证

问自己："如果这件事是错的，我会看到什么？"

- 假成功：命令参数用错，静默返回空，被当成"无残留"（其实是没查）。
- 假失败：检查器按固定块切片解码，把好文件报成坏文件（实测复现过两次）。

相当一部分"故障"其实是检查方法本身有问题。报错先分清是谁在报错。

### 4.3 结论要带版本号和日期

- 任何"某东西在这台机器上不行"的结论，必须带版本号与日期。
- 涉及外部环境的，只说"在我的配置下"，并给一个重测命令。
- 值得重测。环境会变，结论会过期。

### 4.4 交付前，程序验关键属性

人工看一眼不够（有自查工具不等于会自查）。例如处理图片：交付前用几行代码核对四角是否透明、中心是否不透明、主体占比是否合理。我就在这类地方翻过车，把主体抠掉、留下了背景。

### 4.5 自动化检查说干净，不等于真的干净

做过的事：对外发布前跑一个脱敏脚本，按"凭证形态加已知敏感词"扫，报 0 命中，看起来可以发了。

但脚本只查它知道的模式。真实经历：脚本报干净之后，换一批关键词再扫（自己项目的名字、内网 IP、角色名、虚拟机名、路径里的目录名），一次抓到 13 处，包括一个内网 IP、两处项目名、一处角色名。

做法：

1. 机械检查通过后，换一批关键词再人工扫一遍。两批词维度不同：脚本查凭证形态，人查"能认出我是谁、我做过什么"。
2. 关键词清单跟着项目变。新项目、新机器、新账号都会引入新敏感词。
3. 把新发现补进脚本规则，而不是只手工改掉这一处，否则下次重跑还会漏。

推论：检查器的覆盖面本身需要被检查。这和 §4.2 的假失败是同一类问题的两面，一个误报，一个漏报。

## 5 成本：钱和时间花在哪

### 5.1 大头是重复传输，不是写得多

实测：长会话里"把之前读过的内容每步重发一遍"占总 token 的 90% 以上；越长占比越高，150 步以上的会话普遍到 99.5%。

推论：

- 越早读的大文件越贵。第 1 步读的 2000 行，后面每一步都要再付一次。
- 长会话早期绝不读大文件。
- 能不进上下文的，就别让 AI 读进来。

### 5.2 查东西的顺序

```
搜索定位（秒级） > 让子代理去读（原文不进主上下文） > 读全文（最后手段）
```

只在"要改它"或"要逐字精读"时才读全文。否则先定位，只读区间。

### 5.3 本地模型可以当隔断

让本地模型读原文，只把"结论 + 出处"带回来。省的是钱，不是时间（它通常比搜索慢几百倍）。

它适合定位和抽取，不适合判断和权衡。

## 6 一页速查

| 场景 | 做法 |
|---|---|
| 会话要结束 | 写交接件和开篇词；当前态滚动回写 |
| 改完东西 | 同轮记账（时间戳、事件戳、落点、判据；失误也记） |
| 发现两处写同一件事 | 归一为一份，其余留指针。别写"记得同步" |
| 看到重复文件 | 先查是不是软链，再读差异。哈希不同不等于分叉 |
| 要删、要搬 | 先查谁指向它（注意通配前缀漏判）。拿不准只报不删 |
| 派生稿要改 | 先改正本，再重导 |
| 文档过期了 | 标注，不篡改 |
| 要动手删或覆盖 | 问"退得回去吗"。备份要带一条回滚命令 |
| 要删一堆东西 | 先写后删，验证要双条件，skipped 不算证据 |
| 写验收判据 | 命令加期望值，阈值给来源。想不出反例就是假验证 |
| 得到"某东西不行"的结论 | 带版本和日期，只说"在我的配置下"，留个重测命令 |
| 会话变长 | 早期不读大文件，查东西先搜索定位 |

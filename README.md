## 为什么这些坑值得看

三条会反复出现的规律：

1. "看起来一样"不等于"真的没坏"。同一行文字可以是 UTF-8 无 BOM 加 LF、UTF-8 有 BOM 加 LF、UTF-8 无 BOM 加 CRLF 三种存法，在编辑器里长得一模一样，但其中一种会让 `.cmd` 把行碎片当命令执行。所以编码章全是"怎么验证"，不是"应该用哪种"。
2. 报错先分清是谁在报错。相当一部分"故障"其实是检查方法本身有问题：按固定块切片解码会把好文件报成坏文件，漏实现一层解码的工具会把健康数据报成"损坏"。误报比不报更浪费时间，这也是 `tools/` 里那几个校验器存在的原因。
3. 同一事实在多处维护，早晚会分叉。曾有一份文档和它的副本，两处都写着"逐字节相同，改一份必须同步另一份"，写下时是真的，两次核对之后已经 13 处措辞不同。那句声明成了活的假话，还散在 6 个地方。结论：同一事实只在一处维护，其余留指针（见 `docs/06` §2）。

## 怎么用

- 遇到怪现象：先翻 `docs/01` 的速查表，再进对应主题。
- 刚接触命令行或 AI 协作：从头顺序读 `docs/02`。
- 想把 AI 用得更稳：读 `docs/03`，末尾有速查。
- 要做界面或出图：读 `docs/04`。
- 卡在下不下来、装不上：读 `docs/05`。
- 脚本：需要 Node.js 或 Python，都是零依赖单文件，直接 `node` 或 `python` 跑。

文中路径统一写作占位符（`<工作区>`、`%USERPROFILE%`、`<主机名>` 等），替换成你自己的即可。条目末尾"出处"里的 `NN 号 §x.y` 是作者本机的内部笔记编号，按内容理解即可，不必去找那些文件。

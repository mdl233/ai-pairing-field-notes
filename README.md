## 作者的环境（★ 先看这个，再看任何结论）

> 本文里的"快不快""能不能跑""放不放得下"，**都只对下面这台机器负责**。
> 本地模型跑得慢、某个东西"装不上"，**往往不是模型或工具不行，而是环境不同** ——
> 所以把配置**完整摊开**，你按自己的硬件读结论。

| 项 | 值 |
|---|---|
| 系统 | Windows 11 家庭中文版 **25H2**（build 26200） |
| CPU | AMD Ryzen 7 7840HS（8 核 16 线程） |
| 内存 | **32 GB** |
| 显卡 | **NVIDIA RTX 4050 Laptop 6 GB**（笔记本 —— 本文多数"慢/放不下"结论的根源） |
| 本地模型运行时 | **ollama 0.35.1** |
| 在用的本地模型 | `qwen3:4b`（通用/抽取）· `hy-mt2-7b`（翻译）· `nomic-embed-text`（向量） |
| 一个参考实测 | `qwen3:4b` → **51.8 t/s · 100% GPU · 显存 3.1 GB** |
| 网络 | 普通家庭宽带，**不挂代理**（[`05`](docs/05-getting-resources-in-china.md) 的通道可用性表就是这么测的） |

**★ 一个真实的"反例警告"**：同一个模型、同一台机器，我只把 ollama 从 **0.33.3 升到 0.35.1**，速度从 **~5 t/s 变成 51.8 t/s**（差约 **10 倍**）。
所以：**"某模型在本机不可用"这种结论，一定要带版本号和日期，而且值得重测。**

## 为什么这些坑值得看

三条会反复出现的规律：

1. **"看起来一样"不等于"真的没坏"。**
   同一行文字，可以是"UTF-8 无 BOM + LF""UTF-8 有 BOM + LF""UTF-8 无 BOM + CRLF"三种存法——**在编辑器里长得一模一样**，但其中一种会让 `.cmd` 把**行碎片当命令**执行。所以手册里的编码章全是"怎么验证"，而不是"应该用哪种"。

2. **报错先分清"是谁在报错"。**
   有相当一部分"故障"其实是**检查方法本身有问题**：按固定块切片解码会把好文件报成坏文件；漏实现一层解码的工具会把健康数据报成"损坏"。**误报比不报更浪费时间**——这也是 `tools/` 里那几个校验器存在的原因。

3. **同一事实在多处维护，早晚会分叉。**
   我们曾有一份文档和它的"副本"，两处都写着"逐字节相同，改一份必须同步另一份"——**写下时是真的**，两次核对之后已经 **13 处措辞不同**。于是那句声明变成**活的假话**，还散在 6 个地方。
   ⇒ 结论：**同一事实只在一处维护，其余留指针**（详见 `docs/06` §2）。

- **遇到怪现象** → 先翻 `docs/01` 的 **§一 速查表**（按"你看到的现象"查），再进对应主题。

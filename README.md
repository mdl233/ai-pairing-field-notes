## 为什么这些坑值得看

三条会反复出现的规律：

1. **"看起来一样"不等于"真的没坏"。**
   同一行文字，可以是"UTF-8 无 BOM + LF""UTF-8 有 BOM + LF""UTF-8 无 BOM + CRLF"三种存法——**在编辑器里长得一模一样**，但其中一种会让 `.cmd` 把**行碎片当命令**执行。所以手册里的编码章全是"怎么验证"，而不是"应该用哪种"。

2. **报错先分清"是谁在报错"。**
   有相当一部分"故障"其实是**检查方法本身有问题**：按固定块切片解码会把好文件报成坏文件；漏实现一层解码的工具会把健康数据报成"损坏"。**误报比不报更浪费时间**——这也是 `tools/` 里那两个校验器存在的原因。

3. **同一事实在多处维护，早晚会分叉。**
   我们曾有一份文档和它的"副本"，两处都写着"逐字节相同，改一份必须同步另一份"——**写下时是真的**，两次核对之后已经 **13 处措辞不同**。于是那句声明变成**活的假话**，还散在 6 个地方。
   ⇒ 结论：**同一事实只在一处维护，其余留指针**（详见 `docs/03` §3）。

- **遇到怪现象** → 先翻 `docs/01` 的 **§一 速查表**（按"你看到的现象"查），再进对应主题。
